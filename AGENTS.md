# Рабочий процесс выпуска KaskadOS

Явное требование пользователя от 2026-11-04:

- Когда пользователь просит команду сборки изменённого выпуска, сначала автоматически повысить версию Kaskad DE относительно предыдущей сборки. Синхронно обновить `components/kaskad-desktop/VERSION`, `components/kaskad-desktop/release/release.json` и заметки нового выпуска. Проверить согласованность и только затем дать команду сборки. Не ограничиваться предупреждением о старой версии.
- Пользователь запускает сборку сам. Не запускать полную сборку без отдельного указания.
- Когда пользователь присылает лог успешной сборки, следующим шагом дать команду отправки именно собранного выпуска на сервер.
- Установка и обновление выполняются исключительно через серверный репозиторий. Не предлагать прямую установку локальных пакетов (`pacman -U`) или подмену установленных файлов как обычный путь доставки исправлений.
- Сервер: `kaskados-repo@2.26.103.171`, каталог `/srv/kaskados-repo/x86_64/`, публичный адрес `https://repo.kaskados.xyz/x86_64/`.
- Пользователь принципиально не использует SSH-ключи и не хочет, чтобы их создавали или предлагали. Доступ к серверу выполняется только по паролю. Команды `ssh` и `rsync` должны использовать `-o PreferredAuthentications=password -o PubkeyAuthentication=no`. Пароль нельзя добавлять в Git; он сохранён в закрытом архиве перед переустановкой.
- Использовать штатный `scripts/publish-repository.sh`. Он зеркалирует каталог с `--delete-delay`: перед публикацией из новой/неполной рабочей копии скачать текущее серверное зеркало, чтобы не удалить остальные пакеты.
- Не публиковать исправленный выпуск под уже использованным номером версии. Перед выдачей команды публикации сверить версию из лога сборки с ожидаемой версией.
