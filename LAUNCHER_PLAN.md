# Kaskad DE: требования и план переработки лаунчера

Дата: 2026-11-04.
Статус: продуктовые требования по обсуждению с владельцем проекта; реализация не начата.
Основа аудита: commit `54fc29e`, исходники alpha.78. Этот документ дополняет `PRODUCT_AUDIT.md` и уточняет направление работы с лаунчером. Новые решения здесь имеют приоритет над прежними предположениями аудита о нужности Windows-раздела и GPU-действий.

## 1. Цель

Сделать понятное меню для поиска и запуска приложений, с удобным редактированием ярлыков и свободным назначением клавиш. Сократить лишние разделы и специальные сценарии, привести дизайн и анимации к качеству единого продукта Kaskad DE.

Два пользовательских вида лаунчера сохраняются. Само наличие полного и компактного вида не считается дефектом. Проверенная проблема — различия в доступности действий и непоследовательное управление ими.

## 2. Принятые продуктовые решения

| Область | Требование |
|---|---|
| Windows | Убрать отдельный раздел Windows-приложений и управление их окружениями из лаунчера |
| Общий список | Показывать приложения по обычным `.desktop`-ярлыкам независимо от технологии их запуска |
| Proton/Wine | Установщик или пользователь готовит окружение и команду; лаунчер исполняет согласованный контракт ярлыка |
| GPU | Убрать специальные действия «Запустить на дискретной GPU» и принудительный выбор NVIDIA из интерфейса лаунчера |
| Редактор | Дать понятное редактирование ярлыка через ПКМ, без обязательного терминала или текстового редактора |
| Персонализация | Разрешить менять имя, значок и параметры запуска |
| Обновления | Допускается возвращение параметров ярлыка, поставленных обновлённым приложением; механизм не должен зависеть от случайной перезаписи файлов |
| Открытие | Сохранить два вида лаунчера и дать понятное назначение клавиш, включая необязательное одиночное нажатие Super/Win |
| Дизайн | Переработать компоновку и анимации; тёмная Material 3-база, системный акцент, без возврата светлой темы |

Это требования к будущей реализации, а не утверждение, что перечисленное уже работает.

## 3. Граница ответственности

### Пакет, установщик или пользователь

- Устанавливает приложение и необходимые зависимости.
- Готовит Proton/Wine, wrapper-скрипт, рабочие каталоги и переменные, если они нужны конкретному приложению.
- Предоставляет корректный `.desktop` с командой, значком и метаданными.
- Обновляет принадлежащие пакету файлы при обновлении приложения.

Для локальных пакетов Arch обычно используется расширение `.pkg.tar.zst`; установка через `pacman -U` сама по себе не гарантирует настройку Proton. Всё необходимое должно быть предусмотрено содержимым пакета и его зависимостями. Не проектировать универсальный интерактивный Windows-подобный установщик внутри лаунчера.

### Лаунчер

- Обнаруживает ярлыки, показывает приложения, ищет и запускает их.
- Корректно обрабатывает команду, аргументы, рабочий каталог и предусмотренные ярлыком действия.
- Показывает понятную ошибку, если запуск невозможен.
- Позволяет пользователю осознанно изменить ярлык.
- Не скачивает Proton и не создаёт окружение только потому, что пользователь выбрал приложение.
- Не решает самостоятельно, что любое приложение должно запускаться через NVIDIA/`prime-run`.

Игра с командой через Proton остаётся обычным приложением в общем списке. Удаление раздела Windows не означает запрет таких игр.

## 4. Удаление Windows-интеграции из лаунчера

Убрать вкладку/фильтр Windows, выбор EXE, установку и выбор Proton, управление prefixes и связанные инструкции из пользовательских поверхностей лаунчера. Пересмотреть фильтры «Все/Linux/Windows»: без отдельного Windows-раздела разделение по технологии не должно оставаться самоцелью.

Перед изменениями составить карту использования `WindowsAppsView`, `WindowsAppsService` и backend `windowsapps`. Удаление раздела не является разрешением удалить backend, если у него есть другие потребители.

Миграция обязательна:

- Не удалять установленные игры, prefixes, данные и готовые `.desktop`.
- Проверить, не вызывают ли ранее созданные ярлыки удаляемый backend. При необходимости сначала перевести их на самостоятельный поддерживаемый путь запуска либо временно сохранить совместимость.
- Сохранить идентичность ярлыков и привязки закреплённых приложений.
- Сохранённый режим `windows` переводить в общий список приложений, без пустого экрана.
- Удалить недоступные команды, настройки и подсказки согласованно с интерфейсом.

## 5. Редактор ярлыка

Предлагаемое название действия: **«Настроить ярлык…»**. Доступ — через ПКМ и клавиатурное контекстное меню. Это одинаковая возможность для обоих видов лаунчера.

### Основной экран

| Поле | Представление пользователю |
|---|---|
| Название | Обычное текстовое поле |
| Значок | Текущий значок, выбор из темы/файла, возврат исходного |
| Описание | Необязательная краткая подпись |
| Команда запуска | Понятная подпись и пример; техническое имя `Exec` можно показать в пояснении |
| Аргументы | Отдельное понятное управление, синхронизированное с полной командой |
| Рабочая папка | Выбор каталога |
| Терминал | Явная настройка для приложений, которым он нужен |

Расширенные параметры открываются по запросу: переменные окружения в виде пар «имя — значение», полная строка Exec, дополнительные ключи и desktop actions. Не вываливать весь формат `.desktop` на неопытного пользователя.

Обычная форма и расширенное представление должны редактировать одну модель. Если сложную команду нельзя без потерь разложить по полям, сохранить её в расширенном представлении и объяснить ограничение; не упрощать и не переписывать молча.

Пример пользовательского сценария: добавить `prime-run` перед командой конкретного приложения. Это добровольная настройка команды, а не встроенная обязательная GPU-политика. При отсутствии указанного wrapper показать причину; не подставлять другой способ запуска автоматически.

### Сохранение и запуск

- Кнопки «Сохранить», «Отмена», «Вернуть исходные настройки» имеют реальные действия.
- Ошибка валидации показывается у соответствующего поля и не уничтожает введённый текст.
- Сохранение не запускает приложение. Проверочный запуск — отдельное явное действие, если он будет добавлен.
- Изменение вступает в силу без перезагрузки оболочки.
- Изменённая команда применяется при новом запуске; уже работающий процесс не может получить новые параметры задним числом. Не выдавать простую фокусировку старого окна за проверку новой команды.
- Писать изменения атомарно; при ошибке записи сохранять предыдущую рабочую версию.
- Пользовательское редактирование не должно требовать root и напрямую менять файлы, принадлежащие pacman.

### Совместимость формата

Exec имеет собственные правила аргументов, кавычек и кодов `%f`, `%F`, `%u`, `%U` и других; это не произвольная shell-строка. Не разбивать команду простым `split` по пробелам и не добавлять `sh -c` неявно. Источник: [Desktop Entry Specification — Exec](https://specifications.freedesktop.org/desktop-entry/latest/exec-variables.html).

Сохранять неизвестные ключи, локализованные имена, desktop actions и метаданные, которые редактор не менял. Отдельно проверить `DBusActivatable`: явная правка команды должна иметь объяснимый эффект, а не игнорироваться другим путём запуска. Для Flatpak и других wrapper-команд необходима проверка без повреждения исходных аргументов.

## 6. Владение ярлыком и обновления приложения

Пожелание владельца: приложение при обновлении вправе вернуть поставляемый им значок и параметры запуска. Не требовать вечного сохранения всех пользовательских изменений вопреки этому решению.

Техническая оговорка: обновление системного файла и замена пользовательского переопределения — разные операции. Нельзя обещать, что pacman автоматически уберёт изменения, сохранённые отдельно в SessionData или пользовательском `.desktop`. Идентичность desktop entry и выбор между файлами связаны с desktop file ID и порядком поиска: [Desktop Entry Specification — File naming](https://specifications.freedesktop.org/desktop-entry/latest/file-naming.html).

До реализации выбрать и записать одну политику:

1. Где находится каноническая пользовательская версия: пользовательский `.desktop` или существующие overrides с корректной общей моделью. Не оставлять две независимые версии Exec/иконки.
2. Как определяется реальное изменение установленного приложения или исходного ярлыка. Изменение времени файла само по себе недостаточно.
3. Какие изменения возвращаются к версии установщика и когда пользователь узнаёт об этом.
4. Как обрабатываются ярлыки, созданные самим пользователем и не принадлежащие пакету.
5. Как учитываются обновления, выполненные вне интерфейса Kaskad DE, и удаление приложения.

Предлагаемое направление, ещё не окончательное решение: явное состояние «ярлык изменён пользователем», доступный возврат к версии приложения и обнаружение изменения оригинала. Политику автоматического сброса после обновления спроектировать отдельно. Не превращать пользовательское допущение о сбросе в случайную потерю данных или в обязательное сохранение навсегда.

Мигрировать текущие имя, значок, описание, env/аргументы и настройки dGPU без молчаливой потери. Удаление GPU-пункта меню не должно внезапно менять запуск уже настроенных приложений; перенос старого GPU-предпочтения требует проверки доступного wrapper и понятного результата.

## 7. Открытие и горячие клавиши

Два вида меню остаются поддерживаемыми. В настройках лаунчера нужны:

- выбор вида по умолчанию;
- видимая текущая комбинация и её изменение на месте;
- независимое назначение открытия второго вида;
- удаление назначения и восстановление исходного;
- сообщение о конфликте до замены другого действия;
- применение сразу и сохранение после перезапуска/обновления.

В текущем `LauncherTab.qml` уже есть выбор вида и переход к настройкам сочетаний. Это задел, а не доказательство отсутствия настроек целиком. Требование — сделать назначение понятным и непосредственным, используя существующий общий сервис сочетаний вместо нового конкурирующего файла.

Привязка к одиночному **Super/Win** — добровольная возможность, не обязательное новое поведение для всех пользователей. При миграции сохранять существующие назначения.

Ожидаемый контракт одиночного Super:

- срабатывание при отпускании, только если клавиша не участвовала в другой комбинации;
- Super+буква, Super+стрелка и жесты с модификатором не открывают меню дополнительно;
- удержание и autorepeat не вызывают многократных переключений;
- открытый лаунчер по тому же назначению закрывается предсказуемо;
- обработка принадлежит композитору/общему сервису глобальных сочетаний, а не глобальному перехватчику в QML;
- на экране блокировки меню не открывается;
- учитывать левый/правый Super и смену раскладки; поддерживаемые варианты показывать честно.

Общие действия, контекстное меню, фокус и поведение Escape согласовать между видами. Отличия навигации, оправданные списком или сеткой, допустимы; скрытые различия доступных функций — нет.

## 8. Дизайн и анимации

Оценка владельца: текущая компоновка перегружена, дизайн и анимации требуют существенной переработки. Это продуктовая проблема, не просьба слегка поменять цвета.

Требования к следующему макету:

- сначала поиск и приложения, затем редко используемые действия;
- без отдельной Windows-вкладки и GPU-команд;
- понятное различие назначения оставшихся разделов;
- компактная выдача без неоправданно большого пустого пространства;
- стабильный фокус, видимый выбор, понятные состояния загрузки, ошибки и отсутствия результатов;
- согласованные размеры, отступы, акцент и контраст тёмной темы;
- короткие осмысленные анимации без скачков, мигания и задержки ввода;
- повторное открытие/закрытие во время анимации не ломает окно;
- изменение количества результатов не вызывает хаотического перемещения элементов.

Перед серьёзной UI-реализацией подготовить макет или конкретное описание поведения для обоих видов. Проверить небольшой экран, масштабирование и несколько мониторов. Окончательный внешний вид этим документом не утверждён.

## 9. Что из предыдущего аудита остаётся актуальным

| Проблема | Действие в новом направлении |
|---|---|
| Двойное ранжирование теряет совпадения по genericName/ID | Единая семантика поиска и регрессионные сценарии |
| Top-10 до фильтрации; ввод сбрасывает выбранную область | Согласовать область поиска и порядок фильтрации |
| Поиск файлов обещан, но не подключён | Отдельно решить, нужен ли он; не оставлять ложную подсказку |
| Ctrl+P ошибочно выбирает предыдущий раздел | Исправить навигацию и проверить границы |
| Ссылка на отсутствующий extFilterField | Удалить остаточную зависимость в правильном слое |
| Ошибки кавычек, env и desktop actions | Устранить в общем механизме запуска и редакторе |
| Нет обратной связи при отказе запуска | Возвращать результат/ошибку, не считать закрытие окна успехом |
| Некорректная функция очистки истории | Исправить при работе с историей; сейчас вызов в UI не подтверждён |
| GPU-действие активирует старое окно | Сам пункт удаляется; корректность применения новой команды всё равно нужна |

Удаление Windows-раздела не означает автоматическое удаление каталога пакетов. Судьба магазина, поиска файлов и истории этим обсуждением окончательно не решена. Не расширять задачу без основания.

## 10. Критерии приёмки

1. Windows-раздел отсутствует в обоих видах меню, старые приложения продолжают запускаться через обычные ярлыки; данные и закрепления сохранены.
2. Нет специальных NVIDIA/dGPU-действий. Пользователь может задать wrapper в команде; система без NVIDIA не получает неподходящий способ запуска.
3. Редактор доступен мышью и клавиатурой; имя, значок и команда меняются без терминала, сохраняются и применяются предсказуемо.
4. Проверены пробелы и кавычки в путях/аргументах, env со значением из нескольких слов, field codes, терминальные приложения, desktop actions и D-Bus activation.
5. Отсутствующий executable/wrapper, недоступная рабочая папка и ошибка записи дают понятное сообщение; рабочий ярлык не теряется.
6. Проверены пакетный ярлык, пользовательский ярлык, обновление оригинала, удаление приложения, миграция прежних overrides и возврат исходного. Поведение соответствует выбранной политике обновлений.
7. Оба вида лаунчера открываются назначенными клавишами. Одиночный Super не срабатывает после Super-комбинаций и не навязывается существующему пользователю.
8. Нет конфликтов, двойного срабатывания, потери фокуса и расхождения настроек сочетаний между разделами.
9. Проверены малый экран, масштабы 100/125/150/200%, несколько мониторов, повторное открытие во время анимации, смена фокуса и перезапуск оболочки.
10. Наличие кода или успешный unit-test не подменяет runtime-проверку. В отчёте отдельно перечислены проверенные и непроверенные сценарии.

## 11. Порядок работ и ограничения

1. Зафиксировать модель ярлыка и политику обновлений; проверить существующие сервисы и потребителей Windows backend.
2. Спроектировать миграцию готовых ярлыков и пользовательских настроек.
3. Убрать лишние поверхности, сохранив запуск существующих приложений.
4. Реализовать общий механизм редактирования/запуска и исправить подтверждённые ошибки поиска.
5. Добавить непосредственное назначение клавиш через общий сервис.
6. Согласовать макет, затем переработать дизайн и анимации.
7. Выполнить лёгкие проверки и runtime-сценарии; только после этого готовить пользовательское обновление.

Документ сам по себе не разрешает удалять код, приложения, окружения и данные. Реализация ниже начата после отдельного указания пользователя продолжать работу. Полную сборку без прямого запроса не запускать; перед сборкой согласовать VERSION и release-файлы один раз на завершённый пакет изменений.

## 12. Ход реализации — 2026-11-04

Первый этап выполнен в исходниках:

- Удалены WindowsAppsView и его подключения в полном и компактном лаунчере, выбор EXE, фильтры технологии запуска и отдельное сочетание перехода в Windows-раздел.
- Убраны специальные GPU-действия из контекстного меню и панели действий лаунчера. Общий SessionService и существующие предпочтения запуска пока сохранены для совместимости.
- Нормализация старого режима `windows` в `apps` используется всеми тремя окнами и методом переключения режима; старый `files` по-прежнему переводится в `all`.
- Убрана недействительная ссылка extFilterField и обещание поиска файлов из подсказки.
- Windows backend сохранён: ранее созданные ярлыки используют `kaskad-shell windows launch`. Данные, окружения и готовые ярлыки не менялись.

### Второй этап: команда запуска и общий редактор

В исходниках добавлены команда запуска (массив буквальных аргументов), рабочая папка, режим терминала, выбор изображения значка. Редактор подключён к Spotlight. Сохранение сохраняет неизвестные поля существующего override. Ошибки команды показываются в форме; синхронный отказ запуска больше не закрывает лаунчер как при успехе.

Обычный запуск и desktop actions используют общий ApplicationCommand и общий путь SessionService: env, дополнительные аргументы, рабочая папка и терминал обрабатываются одинаково. Desktop action сохраняет собственную команду, а не заменяется основной командой приложения. Для изменённых параметров создаётся новый процесс вместо фокусировки прежнего; приложение с собственной single-instance политикой всё ещё может передать запрос своему существующему процессу.

Вместо execDetached используется наблюдаемый Process для systemd-run; ненулевой код завершения запроса запуска показывает ошибку. Это не проверка дальнейшей работы или появления окна приложения. Унаследованная глобальная shell-приставка сохранена; поле команды приложения не включает shell неявно.

Хранилище остаётся SessionData. Это редактор пользовательских параметров запуска Kaskad DE, а не полноценный редактор исходного `.desktop`: field codes исходного файла по-прежнему обрабатывает DesktopEntries. Экспорт `.desktop`, политика обновлений, атомарность/подтверждение записи SessionData, управление исходными ключами и миграция старого GPU-предпочтения ещё не завершены. Рабочая папка пока вводится строкой; переменные окружения — строкой с проверкой кавычек, не таблицей. Эти ограничения нельзя выдавать за выполнение всего раздела 5.

Проверки: 24 результата Qt Quick Test (включая init/cleanup), интеграционная проверка исходных функций SessionService с mock-зависимостями (фокус/новый запуск, команда, env, terminal, desktop action, ошибка ввода, прежний GPU-путь), синтаксический разбор изменённых QML и git diff --check. ### Третий этап: подтверждение записи, поиск и навигация

- Сохранение и сброс параметров ярлыка дожидаются завершения записи FileView. При отказе возвращается прежнее состояние override, форма остаётся открытой с ошибкой. ### Четвёртый этап: назначение сочетаний лаунчера в Kaskad DE

Подтверждена ошибка native-provider в KeybindsService: сохранение любого действия вызывало `setScreenshotShortcut`, а удаление и сброс также всегда меняли скриншот. Исправлена маршрутизация по конкретному действию. Неподдерживаемое действие теперь отклоняется; изменение действия существующей native-привязки не оставляет исходную привязку скрыто активной.

В композиторе добавлены два QAction с устойчивыми ID `KaskadLauncher` и `KaskadSpotlightBar`, владельцем назначения остаётся KGlobalAccel. Новые клавиши по умолчанию не навязываются. API протокола 27: `launcherShortcut(kind)`, `setLauncherShortcut(kind, shortcut)`, сигналы `launcherShortcutsChanged()` и `launcherRequested(kind)`; kind — `default` или `spotlight`. Пустая строка удаляет назначение. Неизвестное действие, несколько последовательных комбинаций, одиночный модификатор, невалидная или занятая клавиша отклоняются. Старые настройки других владельцев не перезаписываются и не мигрируются автоматически.

Клиент Kaskad.Ipc проверяет версию протокола. PopoutService принимает запросы через тот же путь открытия, что существующие IPC-команды. Общий редактор сочетаний и настройки лаунчера используют единый KeybindsService. В настройках обоих видов добавлены поле сочетания, запись клавиш, явное сохранение и удаление. Esc отменяет запись; уход со страницы прекращает захват; неудачное сохранение оставляет введённое значение с сообщением. Новые элементы доступны только с поддерживающим API композитором и модулем.

Проверено: Node-тест маршрутизации (два вида, сброс/удаление, неизвестное действие, прежний протокол, изоляция скриншота); разбор сочетаний настоящим Qt с подменённым реестром KGlobalAccel (валидные, неверные, конфликт, повторная запись, отказ, удаление); синтаксис новых C++-методов против установленного заголовка KGlobalAccel; `-fsyntax-only` полного IPC-клиента; синтаксис QML и `git diff --check`. Компилировался только маленький временный тест, не компоненты дистрибутива.

Ограничения: одиночный Super ещё не реализован; фактическое срабатывание через KGlobalAccel/D-Bus, захват клавиш в интерфейсе, конфликт с внешним владельцем и восстановление назначения после рестарта не проверены. Для этих проверок нужны сборка и установка обновлённых композитора и Kaskad.Ipc вместе с оболочкой. Текущая пользовательская сессия не менялась. Изменена версия IPC-протокола (26 → 27); версия пакета/release-файлы пока не менялись. Прежние пункты о незавершённой политике `.desktop`, дизайне и GUI-проверках остаются в силе.

### Исправление регрессии запуска после установки alpha.79
