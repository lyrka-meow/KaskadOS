# KaskadOS product audit and cleanup backlog

Этот документ хранит продуктовые решения и подтверждённые проблемы KaskadOS. Он дополняет `INSTALLER_PLAN.md` и не зависит от истории чата.

## Канонические названия

| Сущность | Пользовательское название | Назначение |
|---|---|---|
| Дистрибутив | KaskadOS | Вся операционная система |
| Графическая среда / сессия SDDM | Kaskad DE | Сеанс, в который входит пользователь |
| Оболочка | Kaskad Shell | Панели, док, рабочий стол, лаунчер, виджеты и системные поверхности |
| Композитор | Kaskad Compositor | Оконный менеджер и Wayland-композитор Kaskad DE |
| Портал | Kaskad Portal | Внутренний XDG desktop portal |

`KaskadOS` не должно быть названием графической сессии. SDDM должен показывать `Kaskad DE`.

`Kaskad DE`, `Kaskad Shell`, `Kaskad Compositor` и `Kaskad Portal` — публичные имена. Нижний регистр и формы без пробелов допустимы во внутренних путях, application ID, DBus, QML URI, именах бинарников и пакетов. Технические термины `.desktop` и XDG Desktop Portal не являются брендом.

Финальный критерий приёмки бренда — на пользовательских поверхностях нет чужих или внутренних имён, а контрактные технические имена меняются только как атомарная миграция.

Глобальный search-and-replace без карты зависимостей запрещён: текущие идентификаторы связывают композитор, shell, portal, сборку и пакетирование. Переименование выполняется как единая техническая миграция:

1. определить канонические пути, application IDs, QML URI, команды, service names и config names семейства Kaskad;
2. переименовать исходные каталоги и build targets;
3. одновременно перевести композитор, shell, portal, session, packaging, tests и scripts;
4. заменить пользовательские названия и SDDM session;
5. выполнить чистую сборку и тесты уже только с новыми именами;
6. проверить отсутствие запрещённых строк и старых путей в исходниках и собранном пакете.

Если обновление существующей установки требует одноразового переноса пользовательской конфигурации, он проектируется отдельно и удаляется из основной кодовой базы после переходного выпуска. Он не является оправданием постоянного сохранения чужого бренда в проекте.

## Принципы продукта

- Тёмный Material 3 — единственная поддерживаемая цветовая база Kaskad DE.
- Светлый режим, расписание light/dark и отдельные light icon-theme branches удаляются согласованно, а не только скрываются в UI.
- Акцентная обводка окон по умолчанию выключена, но доступна как явная настройка.
- Рабочая функция без понятного пользовательского сценария не добавляется в интерфейс.
- Неработающие controls и будущие заглушки не показываются.
- Одна функция имеет одного владельца и одну реализацию; настройки не дублируют редактор.
- Аппаратно-зависимые действия показываются по capability, а не по наличию случайного бинарника.
- Неизмеримый прогресс показывается indeterminate-состоянием, а не выдуманным процентом.

## P0 — мешает обычной работе

### Неконтролируемая прокрутка

Симптом: небольшой поворот колеса способен перебросить список в конец.

Подтверждённый кандидат: общий слой `kaskad-qml-common/KaskadCommon/Widgets` усиливает `pixelDelta` коэффициентом `3.5`, добавляет собственную инерцию и различает мышь/тачпад только по наличию `pixelDelta`. Это ещё требуется подтвердить записью входных событий; диагноз нельзя считать окончательным без воспроизведения.

Исправление:

- тестовое окно записывает тип события, `angleDelta`, `pixelDelta`, phase, velocity и `contentY`;
- системная инерция не дополняется второй инерцией оболочки;
- mouse wheel и touchpad обрабатываются раздельно;
- общий компонент проверяется на длинном списке приложений, VPN и Settings.

## P1 — архитектурные и вводящие в заблуждение дефекты

### Редактор рабочего стола

- Редактор охватывает desktop и panel, но не отдельный Dock.
- Dock попадает в неполный undo snapshot, хотя операций его редактирования нет.
- Размещение panel/dock частично осталось в Settings и частично находится в редакторе.
- Статический каталог позволяет добавить неподдерживаемые виджеты, включая Mango-only layout widget.

Целевой контракт описан в `INSTALLER_PLAN.md`: видимый вход, выбор объекта левым кликом, локальный inspector, каталог добавления, единая транзакция и полный undo/redo. Dock является полноценным редактируемым объектом.

### Реестр виджетов

Вместо ручных списков нужен единый registry:

- id и пользовательское название;
- поддерживаемые compositor/backend;
- runtime availability;
- причина недоступности;
- настройки;
- действие по клику;
- допустимые поверхности: panel, dock, desktop;
- правила уникальности.

Виджет без backend или пользовательского сценария не показывается. Удаление каждого спорного виджета принимается по инвентаризации, а не по количеству исходных файлов.

### Батарея и питание

- Battery widget сейчас всегда видим.
- По умолчанию он добавляется только если UPower сообщает реальную батарею или UPS. На настольном ПК без источника питания его нет; пользователь может добавить доступный widget вручную, если capability появляется.
- Текущий список «потребляющих» процессов фактически показывает CPU и память. Это не энергопотребление.
- Блок процессов удаляется из battery popout до появления настоящего per-application energy backend.
- Battery popout оставляет честные данные: заряд, состояние, время, общий power draw/charge rate, health и power profile.

### GPU

- GPU widget сейчас открывает список процессов вместо информации о GPU.
- Клик должен открывать hardware/GPU details конкретного устройства.
- `Запустить на дискретной GPU` показывается только при подтверждённом offload-capable GPU.
- Одноразовый запуск и постоянное предпочтение GPU — разные действия.
- Уже запущенное приложение нельзя просто сфокусировать и выдавать это за новый запуск на другой GPU.

### Launcher и данные приложений

- Текущий редактор хранит private shell override, а не редактирует desktop entry.
- Реальные name/icon/description используются как placeholder; поля Exec нет; выбор файла иконки отсутствует.
- Dock игнорирует launcher override, поэтому имя и иконка расходятся.

Нужен единый resolved application record для launcher, dock, file associations и search. Редактор показывает текущие значения, preview и picker иконки, команду запуска и дополнительные параметры. Локальные изменения сохраняются в корректной пользовательской desktop entry с миграцией существующих overrides.

### Windows/Proton

Встроенная вкладка и менеджер Proton удаляются как продуктовая функция. Windows-приложение поставляется нормальным пакетом вместе с нужным runtime и desktop entry.

Удаление должно:

- убрать Launcher и Spotlight surfaces;
- убрать EXE interception либо направить его в обычный association flow;
- не удалять пользовательские prefixes и runtime без отдельного запроса;
- не оставлять мёртвые backend actions.

### Установка приложений и прогресс

Текущий общий процент синтетически распределён по стадиям и маркируется `≈`. Вместо этого:

- показывается текущая стадия;
- при наличии данных — bytes/total или packages N/M;
- при неизвестной длительности — indeterminate progress;
- local package, repository, Flatpak и AUR используют один визуальный компонент;
- запуск установки из Files немедленно создаёт доступную пользователю карточку операции.

### Аудио и видео из Files

Files уже вызывает `gio open`, но defaults для audio/video не заданы и собственный player не получает выбранный файл.

Требования:

- double-click открывает конкретный файл в назначенном приложении;
- при отсутствии association открывается выбор приложения с `Использовать по умолчанию`;
- пути с пробелами и playlist handoff тестируются end-to-end;
- видеоплеер — самостоятельная функция, а не пустая кнопка.

### Настройки и VPN

Карта Settings строится вокруг технических модулей, а не задач пользователя. Новая верхняя структура:

1. Рабочий стол и панели
2. Оформление
3. Дисплеи
4. Сеть и общий доступ
5. Звук
6. Приложения
7. Устройства
8. Система
9. Конфиденциальность и безопасность

VPN получает компактный overview, отдельный searchable/virtualized список серверов, отдельную detail page профиля и раскрываемую диагностику. Длинные технические инструкции не находятся в основной форме.

### Темы

- Online theme registry и его UI/RPC удаляются.
- Локальные и встроенные палитры сохраняются.
- Существующий пользовательский registry theme сначала материализуется локально, чтобы после миграции не получить пустую тему.
- Light mode, auto light/dark и отдельные light icon themes удаляются.
- Все portals и приложения получают последовательный dark preference.

### Акцентная обводка

Default меняется на false одновременно в SettingsData, SettingsSpec и compositor decoration defaults. Сохранённое пользовательское `true` не сбрасывается.

## Готовые раскладки

Импорт/экспорт `.kaskadlayout` уже существует, но это транспорт, а не готовый onboarding.

Встроенные профили не копируют чужой визуальный язык. Все используют Kaskad Material 3 и различаются знакомой геометрией:

1. **Kaskad** — рекомендуемая собственная компоновка.
2. **Классическая** — нижняя панель, меню и задачи в привычных местах.
3. **Панель и Dock** — верхняя системная панель и нижний dock.

В приветственном сценарии пользователь видит preview и выбирает профиль либо импортирует `.kaskadlayout`. Выбор не блокирует дальнейшее знакомство с системой и его можно позже изменить в редакторе.

Профиль обязан содержать panel, dock, desktop widgets, monitor/workspace scope и appearance параметры, поддерживаемые текущей версией формата. Применение транзакционное и полностью отменяемое.

## Сеть и общий доступ

Нужен отдельный пользовательский сценарий `Поделиться интернетом`, а не набор технических переключателей:

- выбрать источник интернета: Wi-Fi, Ethernet или VPN;
- выбрать, куда отдавать: Ethernet или Wi-Fi hotspot;
- показать конфликт, если один интерфейс нельзя одновременно использовать в обеих ролях;
- автоматически создать корректный NetworkManager shared connection;
- показать адрес, DHCP/NAT status и подключённые устройства;
- дать `Остановить общий доступ` и восстановить предыдущее состояние;
- диагностика объясняет отсутствие carrier, upstream, DNS или NAT.

Безопасная проверка backend выполняется отдельно; UI не должен сам собирать shell-команды маршрутизации.

## Системный монитор

Процессы, hardware/GPU, ресурсы и питание — разные назначения.

- Processes показывает понятные application groups и позволяет раскрыть отдельные процессы.
- Resources показывает CPU, memory, disk and network.
- GPU widget открывает GPU details, не случайный process popout.
- Battery показывает только реальные power metrics.
- Переходы между этими экранами используют единый system-monitor route contract.

## Порядок работ после установщика

1. Зафиксировать capability registry и карту владельцев настроек.
2. Исправить общий scroll layer и покрыть его тестом.
3. Провести полную техническую миграцию бренда, включая пути, targets, services, QML URI и SDDM session; запрещённые старые названия должны исчезнуть из исходного дерева.
4. Выключить outline default во всех слоях.
5. Довести editor object model, включая Dock, и удалить дубли размещения из Settings.
6. Перестроить Settings navigation и VPN surfaces без изменения рабочего backend.
7. Ввести единые application metadata и launcher editor.
8. Исправить GPU capability/action и hardware routes.
9. Упростить Battery popout до честных метрик.
10. Удалить Proton manager и online theme registry с миграцией данных.
11. Сделать честный progress model и file-association flow.
12. Добавить встроенные Kaskad layout profiles и onboarding.
13. Проверить нулевое число старых брендовых идентификаторов в исходниках и собранных артефактах.

Каждый пункт принимается по пользовательскому сценарию и автоматической проверке, а не по наличию control в интерфейсе.
